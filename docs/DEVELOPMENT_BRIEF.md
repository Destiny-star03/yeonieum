표기: **C = 사용자에게서 확인된 방향**, **R = 원 대화의 권장안**, **P = 이번 브리프의 보완 제안**, **O = 미결정**. R/P는 구현 논의를 위한 기준안이며 사용자 확정사항과 구분한다. 별도 표시 없는 상세 설계·수치는 P다.

원문에는 ‘첫 번째 버전 완료 조건 8가지’라는 문구만 있고 세부 목록이 없다. [테스트·시연 기준](ACCEPTANCE.md)의 8개 완료 조건은 이를 보완해 작성한 P이며 원문의 복원본이 아니다. 과거 커플 앱·분실물 서비스는 현 개발 범위에 포함하지 않는다.

## 2. 목표, 범위, 사용자

기존 임원에게 연락해 파일을 찾거나 매년 개인 저장소를 복사하는 부담을 줄인다. 조직·학년도·행사별 자료와 예산을 한 포털에서 관리하고, 다음 임원이 기록을 읽고 업무를 시작할 수 있어야 한다.

초기 개발·시연은 **학과협의회부터** 시작한다(C-16). 총학생회는 조직 격리 검증용 가상 비교 단체로 사용할 수 있다(P). 실제 시범은 그중 1~2개 조직부터 시작하고 나머지 조직도 동일 모델로 수용한다. 담당 선생님의 전체 운영 현황 확인과 조직별 제한을 구분하며 단체 간 상하 관계는 추정하지 않는다.

확인된 구성은 각 단체의 최고 책임자, 총학생회·신문방송국의 부장·차장, 학과협의회의 학회장·부학회장·반대표, 연합동아리의 일반동아리장·동아리원과 학생성공센터 담당 선생님이다. 첫 버전은 이들 중 운영 담당자를 중심으로 사용한다(C-11). 담당 선생님이 4개 최고 책임자 권한을 부여하고, 각 최고 책임자가 자기 단체의 하위 역할을 부여한다(C-12/13). 학회장은 부학회장·반대표를 직접 지정한다(C-14). 의장(학과협의회장)은 자기 학과 학회장을 겸한다(C-15). 참여 하위 직책과 자료·회계 기능은 추가 확인한다. 단체 간 상하 관계나 총학생회의 타 단체 감독권을 부여하지 않는다. 일반 학생 공개 포털은 초기 범위 밖이다.

최신 조직 구조와 사실/제안/미결정 구분은 [조직 구조·운영 주체](ORGANIZATION_MODEL.md)를 따른다.

### 회계 규칙 (C와 구현 제안 P)

- 첫 버전은 단체별 연간 예산·행사 배정·실제 지출을 다룬다. 학과·개별 동아리 독립 장부는 후속이다(C, Q5).
- 등록자·실제 집행 담당자·확인자를 구분한다. 일반 지출은 확인 권한·범위가 있으면 본인 건도 확인 가능하다(C, Q19/27). 초과분 예외 확인은 해당 단체 최고 책임자가 맡고 그 책임자 본인 집행 건은 선생님이 확인한다(DM-C03). 대리 등록해도 실제 집행자를 기준으로 한다.
- 실제 발생 금액은 검토 대기·반려·초과 여부와 별도로 보존한다. 초과 기록을 거부하거나 반려로 실제 사용액을 없애지 않으며 예산도 자동 증액하지 않는다(C, Q21~22/50~51).
- 개별 지출 검토 결과·초과분 처리 결과·전체 정산 확정은 별개다. 선생님이 미처리 항목을 확인·처리한 뒤 정산 확정하며 미완료 항목이 있으면 확정할 수 없다(C, Q20/52).
- 변경 전후 내용·최종 반영 금액을 추적하고 확정 정산 원본과 증빙에는 별도 수정·삭제 제한을 둔다(C, Q16/23/25).
- 잔액은 연간 예산 또는 행사 배정액에서 해당 범위 실제 집행액을 뺀 금액이다(C, DM-C04). 검토 대기·확인 완료·반려를 모두 실제 집행액에 포함하고 현재 상태별 금액을 별도 표시한다. 잔액이 음수면 초과액은 그 절댓값이며 아니면 0이다. 상태 변경만으로 실제 집행액·잔액이 달라지지 않는다.
- 배정액이나 이미 집행액에 포함된 검토 대기액을 다시 지출로 합산하지 않는다. 같은 지출의 수정·재제출 회차도 현재 반영 금액을 한 번만 집계한다. 금액은 KRW 정수 방식을 제안한다(P). 환불·정정 반영 시점과 권한은 O-04에서 결정한다.
- 재시도·동시 확인 때 판정과 집계가 중복되지 않도록 처리한다(P). 미검토·반려 실제 지출을 잔액에서 제외하는 이전 계산안은 DM-C04로 대체했다.

### 인수인계 규칙 초안 (R/P, O-03·O-12 결정 대상)

1. 전년도→다음 운영기 또는 같은 운영기의 중도 담당자 교체를 연결한다. 새 운영기·후임 생성만으로 권한을 일괄 복제하지 않는다.
2. 인계자가 문서 버전, 확정 정산, 계속할 업무, 주의 사항을 체크리스트로 묶어 제출한다.
3. 지정 책임자가 인수자와 역할을 승인한다. 임시 인수 접근이 필요하면 범위·기한을 별도 부여한다.
4. 인수자는 허용된 과거 자료를 열람하고 필수 항목을 확인한다. 역할 부여 승인과 인수 확인을 별도 기록하고 미완료 항목이 있으면 완료하지 않는다. 대리 작성 사실이 인수 확인을 대체하지 않는다(Q18/29).
5. 기존 역할은 자신의 임기 종료 또는 명시적 회수 시점부터 업무 권한이 종료된다. 의장은 자기 학과 학회장 자격 종료에도 종료된다. 인수인계 미완료가 기존 권한을 무기한 연장하지 않는다. 유예는 별도 승인한다.
6. 후임의 유효 역할과 담당 범위로 허용되는 같은 조직의 과거 자료를 읽는다(Q7). 영수증·민감 문서는 회계 역할 등 추가 제한을 적용한다. 과거 운영기의 원본 수정권은 자동 승계하지 않는다.
7. 조직 자료 ID·소유 조직과 감사 이력을 유지한다. 계정 삭제·비활성화는 조직 자료를 삭제하지 않는다. 중도 교체에도 같은 원칙을 적용한다.

## 4. 권한 체계 초안

**S10의 확정사항:** 담당자 중심 사용, 담당 선생님은 서비스 관리자, 선생님이 4개 최고 책임자 역할을 부여, 최고 책임자가 자기 단체의 하위 역할을 부여한다. S11/S12에서 학회장의 부학회장·반대표 지정과 의장·학회장 겸임을 추가 확정했다. [역할·권한 명세](ACCESS_CONTROL.md)의 확정 부여표를 따른다. 아래의 기능별 권한 매트릭스는 계속 P이며 확정 역할 부여 체계를 바꾸지 않는다.

역할명과 매트릭스는 **P**다. 학생회장·의장·국장·연합동아리장은 확인된 직책이고, 권한 묶음과 별도로 관리한다. 최고 책임자의 자기 단체 예산 관리 권한을 명세에 반영해야 하지만 간부의 회계 입력 권한은 별도로 부여하고 일반 지출 본인 확인은 허용한다. 초과분 예외 절차와 권한 묶음은 O-02/O-04에서 구체화한다.

단체별 직책 순서는 C-08의 조직 구조다. 아래 역할은 직책명과 일대일 대응하지 않으며, 동아리원을 자동으로 EDITOR로 매핑하거나 상위 직책에 하위의 모든 자료 열람권을 부여하지 않는다. 반대표는 학과→학년→반 범위다(DM-C01). 실제 소속 목록·정원과 개별 동아리 상세는 O-13에서 정한다.

담당 선생님은 C-09/12에 따라 서비스 관리자다. 아래 PLATFORM_ADMIN은 기술 배포·장애 대응 권한의 기존 제안이며, 서비스의 사용자·역할 관리 권한과 구분한다. 서비스 관리자는 전체 운영 현황·감사 조회·전체 정산 확정 범위를 갖고 민감 자료 열람은 별도로 구체화한다. 최고 책임자는 자기 단체 하위 역할을 부여하고, 학회장은 부학회장·반대표를 부여한다. 그 밖의 하위 담당자 재위임은 첫 버전에서 제공하지 않는다(Q12). 의장과 자기 학과 학회장은 동일 사용자의 별도 역할로 표현한다. 사용자는 여러 소속과 역할을 가질 수 있다.

초과분에서 최고 책임자 본인이 실제 집행한 건의 예외 확인은 담당 선생님이 수행한다(DM-C03). 전체 정산 확정은 담당 선생님의 별도 업무 권한이다(Q52). 위 표의 지출 확인자 역할로 자동 확정할 수 없다. 일반 자료 권한으로 영수증·개인정보를 자동 열람할 수 없다(Q24).

위 ‘허용’에는 다음 조건이 모두 적용된다.

- 계정 활성, 소속 승인, 서버 시각 기준 `starts_at <= now < ends_at`이고 역할 활성 이후, 의장은 선출·서비스 부여 이후, 미회수 상태, 대상 담당 범위·기록 상태에 대한 권한 충족. 학년도 분류가 역할의 유효기간을 자동 결정하지 않음. 계정 로그인 성공만으로는 충분하지 않다.
- 작성·수정은 현재의 열린 운영기에 한정한다. 과거 운영기는 읽기 및 승인된 정정만 허용한다. 파일·영수증·버전·공유·검색·집계·내보내기에도 같은 검사를 적용한다.
- 학회장의 부학회장·반대표 지정은 자기 학과 범위로 제한한다(C). 의장 겸임자의 협의회 범위 권한과 학회장 단독 역할의 자기 학과 범위를 별도로 판정한다. 의장 역할과 학회장 역할은 담당 범위를 구분해 기록하되 공식 임기는 같다(DM-C05). 의장은 학회장들에 의해 투표로 선출되고 선생님이 선출 결과에 따라 서비스 역할을 부여한다. 자기 학과 학회장 자격 종료 시 의장도 종료한다(DM-C02).
- 최고 책임자는 자기 단체의 하위 역할만 부여하는 기준을 적용한다. 타 단체·서비스 관리자·동급 최고 책임자 권한 부여, 자기 권한 확대는 허용하지 않는 P다. 최고 책임자 임명은 담당 선생님이 수행한다. 최초 관리자·회수·재위임·회계 기능 권한은 O-02/O-12에 따라 결정한다.
- 공통 공유는 인증된 지정 조직의 읽기 허용이다. 누구나 읽는 인터넷 공개와 다르며, 공유받은 조직이 원본을 수정하거나 재공유하지 못한다. 공유 철회 후 신규 접근을 차단한다.
- Cognito는 신원 확인에 사용하고, 조직·임기·동적 역할은 애플리케이션 DB에서 판정하는 R/P다. JWT에 남아 있는 이전 역할만 믿지 않는다.
- 회수 후 다음 API 요청과 신규 파일 URL 발급을 차단한다. 이미 발급한 Presigned URL은 유효기간 동안 사용될 수 있으므로 제안 TTL은 최대 5분이다. 즉시 파일 차단이 필요한 정책이면 인증 프록시 등 다른 전달 방식을 검토한다. [AWS Presigned URL 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
- URL 발급 이력은 ‘다운로드 권한 발급’이다. 사용자가 파일을 끝까지 읽었다는 증거와 구분한다.

| AuditEvent | id, actor_id?, actor_label, organization_id?, action, target_type, target_id, occurred_at, request_id, change_summary | 업무 이력 추가 전용. 민감 원문·토큰 저장 금지 |
| ProcessedEvent / OutboxEvent | dedupe_key, target_id, status, attempts, created_at | 파일 이벤트 중복 억제 / DB 저장과 알림 발행 사이 유실 방지. 비동기 도입 시 추가 |

직책과 소속·업무 역할을 구분하고, 직책 이력과 역할별 범위·기간을 연결하는 안이다. 학회장의 역할 부여 범위 검증을 위해 최소한 학회장과 자기 학과의 연결은 필요하다. 반대표는 학과→학년→반을 담당한다(DM-C01). 하위 단위별 자료 열람의 세부 경계는 추가 검토한다. 실제 하위 단위 목록·정원·자료별 세부 범위는 O-13 미정이며 현재 표를 최종 ERD로 확정하지 않는다.

`?`는 선택 필드다. 일부 엔터티의 조직·운영기는 부모에서 도출할 수 있다. 물리 모델에서 중복 저장한다면 복합 외래키 등으로 일치를 강제한다.

관계 요약:

```text
User ─ Membership ─ Organization / OrganizationUnit
Membership ─ MembershipRole ─ prerequisite MembershipRole (의장 자격)
Organization ─ OrganizationTerm ─ AcademicYear
OrganizationTerm ─ Folder / Event ─ Document ─ DocumentVersion ─ FileObject
OrganizationTerm ─ AnnualBudget ─ BudgetAllocation ─ Expense ─ ExpenseRevision
ExpenseRevision ─ ExpenseAttachment ─ FileObject
ExpenseRevision ─ ExpenseReviewDecision
OrganizationTerm ─ Settlement ← AccountingCorrection → 원 지출
Organization ─ Handover(from_assignment, to_assignment) ─ HandoverItem
Document ─ DocumentShare ─ target Organization
각 변경 행위 ─ AuditEvent
```

구현 시 지켜야 할 무결성:

- 문서·폴더·행사·배정·지출·증빙·인수인계의 조직 범위 일치를 서버와 DB에서 검증한다. 문서와 폴더·행사, 배정과 지출 등 같은 운영기에 속해야 하는 관계는 운영기도 일치시킨다. 인수인계는 서로 다르거나 같은 출발·도착 운영기를 허용하며 이전 운영기의 문서·정산 참조를 보존한다. 각 운영기와 항목의 단체·담당 범위·열람 자격을 별도로 검사하고 타 조직 ID 끼워 넣기는 거부한다.
- 사용자/소속 종료 시 조직·문서·예산·정산·감사 이력의 `ON DELETE CASCADE`를 금지한다. 개인정보 삭제는 작성자 식별정보의 가명화 등 별도 정책으로 처리한다.
- 금액 합계·승인 전이·예산 감액·소속 활성화/회수·인수인계 완료는 동시성을 고려한 트랜잭션으로 처리한다. 감사 이벤트도 성공한 변경과 함께 커밋한다.
- UTC 시각 저장, 화면은 Asia/Seoul. 학년도와 날짜만 있는 지출일은 시간대 변환 대상과 구분한다.
- 검색 인덱스는 조직·운영기·문서 유형·제목·상태, 회계는 배정·상태·일자 중심으로 제안한다. 권한 필터를 페이지 처리·집계보다 먼저 적용한다.
- 인수인계는 기존 자료 참조를 보존한다. 새 운영기에는 새 예산·새 문서를 만들며 전년도 지출을 당해 연도 지출로 복사하지 않는다.

## 6. 화면·API 구현의 경계

화면 초안은 로그인/초대 확인, 조직·학년도 선택, 조직 대시보드, 자료실·상세·버전, 예산·지출·승인함, 인수인계 목록·상세, 조직 구성원 관리, 운영 상태 화면이다. 조직과 학년도 선택은 탐색 편의이며 인가의 근거가 아니다.

REST 경로 초안은 `/organizations/{org_id}/terms/{term_id}/...` 아래 `documents`, `upload-sessions`, `budgets`, `expenses`, `handovers`, `memberships`를 둔다. 승인·반려·정산 확정·역할 회수는 명시적 명령으로 처리한다. 리소스 ID만 받는 경로도 소유 조직을 조회하여 검사한다.

오류는 인증 실패 401, 권한 실패 403 또는 존재 노출을 막는 일관된 404, 충돌·종료된 상태 409, 잘못된 입력 422 등으로 계약을 정한다. 페이지 크기 상한, 요청 추적 ID, 동시 수정 충돌, 제출·승인 중복 요청 처리 규칙을 API 명세에 담는다. 최종 경로·어댑터·라이브러리 버전은 구현 전 결정한다.

## 7. AWS 아키텍처 권장안

아래는 **R/P의 배포 후보**다. 프론트엔드와 API 실행은 서버리스 중심이지만 RDS·네트워크는 상시 비용이 발생할 수 있는 관리형 자원이다. 전체를 ‘유휴 비용 없는 서버리스’로 간주하지 않는다.

```text
브라우저 ─HTTPS─ CloudFront ─OAC─ S3 웹 버킷 (비공개, 정적 빌드)
   ├─ Cognito (로그인, 토큰)
   ├─ API Gateway (토큰 검증)
   │     └─ Lambda / FastAPI 연동 어댑터 (업무 인가)
   │            ├─ VPC 내부 RDS PostgreSQL (연결 수 제어, Proxy 검토)
   │            ├─ 파일 URL 서명 / 파일 메타데이터
   │            └─ CloudWatch 로그·지표·알림
   └─ 권한 확인 후 발급된 URL ─ S3 문서·증빙 버킷 (비공개)
                                       └─ SQS Standard ─ Lambda 파일 처리 ─ DB 상태
                                              └─ DLQ (실패 대기열)

선택 확장: 승인 이벤트/Outbox ─ SNS 또는 Step Functions ─ 알림
           EventBridge Scheduler ─ 정기 보고서 Lambda
공통 기반: IAM 최소 권한, VPC·Security Groups, 비밀정보 관리, 백업, 비용 관리
```

### 서비스별 역할과 선택 조건

| 영역 | 권장안 | 구현·검증 포인트 |
|---|---|---|
| 웹 | React + TypeScript, Vite 후보 / S3 + CloudFront | 정적 빌드, HTTPS, SPA 라우팅, 배포 롤백. 문서 버킷과 웹 버킷 분리 |
| 인증 | Cognito | 가입 정책·MFA·계정 복구 결정. 인증과 업무 인가 분리. 학교 SSO는 별도 |
| API·계산 | API Gateway + Lambda / Python + FastAPI | HTTP API/REST API의 인증·비용·제한 비교, Lambda 어댑터와 런타임 검증. 장시간 파일 처리는 요청에서 분리 |
| 데이터 | RDS PostgreSQL 우선 | 관계·트랜잭션·집계 장점. Private DB, TLS, 마이그레이션, 연결·동시성 제한 |
| 파일 | 비공개 S3, Versioning, 짧은 Presigned URL | 공개 차단, 서버 지정 객체키, 형식·크기·체크섬 검증, 실제 버전 ID와 문서 버전 연결 |

### 연결과 보안에서 빠뜨리면 안 되는 사항

1. **웹 원본과 업무 파일을 분리한다.** CloudFront OAC는 S3 원본 보호이며 조직별 업무 인가를 대신하지 않는다. 웹은 일반 S3 버킷 원본을 사용한다. S3 website endpoint에는 OAC를 적용할 수 없다. [AWS OAC 문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html)
2. **Lambda ↔ RDS 연결을 실험한다.** 같은 VPC의 허용된 Security Group 경로에서 DB에 접근하고 동시 연결 수를 제한한다. RDS Proxy는 연결 풀 후보로 비용·권한·부하를 비교한다. 단순 실습에서는 제한된 직접 연결도 검토한다. [AWS Lambda–RDS 문서](https://docs.aws.amazon.com/lambda/latest/dg/services-rds.html)
3. **VPC 외부 서비스 경로를 명시한다.** DB 연결 Lambda가 S3·SQS·비밀정보 등 필요한 API에 접근하는 방법을 VPC endpoint 또는 NAT 등으로 설계하고 비용을 산정한다. 퍼블릭 서브넷 배치만으로 해결된다고 가정하지 않는다. JWT의 외부 키 조회 등 필요한 outbound도 확인한다.
4. **업로드는 준비 → 전송 → 검증 → 권한 있는 사용자에게 제공 가능한 상태로 나눈다.** API가 업로드 세션과 객체키를 만든 뒤 브라우저가 직접 S3로 전송한다. 클라이언트 완료 신호만 믿지 않고 파일·크기·체크섬·버전을 서버에서 확인한다. `PENDING → PROCESSING → READY | REJECTED`를 표시하고 READY 전 다운로드·증빙 제출을 제한한다. 검사 방식은 O-09에서 결정하며 메타데이터 확인을 악성파일 검사 완료라고 표현하지 않는다.
5. **서명 URL을 일회용이라고 부르지 않는다.** 만료까지 재사용될 수 있다. 업로드 객체키 재사용·덮어쓰기를 고려하여 불변 버전키와 저장소 버전 ID를 고정하고, 서버가 검증한 버전만 다운로드한다. URL·토큰을 로그에 저장하지 않는다. [AWS Presigned URL 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
6. **파일 이벤트는 중복·지연·역순을 허용하는 소비자로 처리한다.** 객체/버전 기반 멱등키, 같은 객체의 순서 비교, 처리 결과 조건부 갱신과 DLQ 재처리를 설계한다. S3 알림은 적어도 한 번 전달되며 Standard SQS를 직접 연결한다. FIFO가 필요하면 별도 라우팅을 검토한다. [AWS S3 알림](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html), [이벤트 순서 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html)
7. **버전 관리와 복구 계획을 함께 만든다.** S3 Versioning은 이전 객체 복원에 쓰고, 비용·삭제 권한·보존 정책을 별도 설정한다. RDS 시점 복구는 새 DB 인스턴스를 만들므로 연결 전환·문서 버전 정합성까지 훈련한다. 버전 관리만으로 모든 삭제·계정 사고에 대비한 독립 백업이 완성되지는 않는다. [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html), [RDS 시점 복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

### 환경·비용·대안

- 로컬 개발은 PostgreSQL과 테스트 파일 저장소/스토리지 어댑터로 핵심 규칙을 검증하는 안이다. 로컬 모의 통과와 실제 AWS 통합 검증을 구분한다.
- 과제 계정에서 Cognito·IAM·VPC·RDS·SQS 등 생성·실행 권한과 세션/계정 종료 조건을 확인한다. Learner Lab을 장기 운영 계정으로 전제하지 않는 R-05를 유지한다. 정확한 이용 제약은 해당 수업 계정에서 확인한다.
- 리전·DB 사양·가동 시간·파일/버전 용량·트래픽·로그 보존량을 정한 뒤 견적을 낸다. RDS·Proxy·NAT·VPC endpoint·백업 비용을 포함한다. 무료 운영이나 특정 월 비용을 보장하지 않는다.
- 월 상한과 알림 수신자를 O-05에서 결정한다. 예산 알림은 비용을 강제로 차단하는 장치로 취급하지 않는다. 임시 자원 종료 전 데이터 내보내기·복구 가능 여부를 확인한다.
- RDS 비용·권한이 맞지 않으면 DynamoDB를 비교할 수 있으나 승인 원자성·관계·집계·조회 패턴을 다시 설계해야 한다. DB만 교체하면 된다고 가정하지 않는다.
- 수업에서 EC2/ALB/Auto Scaling 시연이 실제로 요구될 때 계산 계층 대안을 검토한다. 기존 사례에 등장했다는 이유만으로 필수 기능으로 추가하지 않는다.

## 8. 비기능 요구 초안

보안·보존의 원칙은 S3/S4의 R이고 구체 수치는 P다. 학교의 보유 의무나 법적 기준을 대신 정하지 않는다.

|---|---|---|
| N-01 | 조직 격리·최소 권한 | 모든 업무·파일 경로를 서버 인가. 타 조직 검색 결과·건수·증빙·버전 유출 0건. 운영 IAM도 업무별 최소화 |
| N-02 | 개인정보·비밀 보호 | HTTPS, 저장 암호화 구성, 비밀 저장소 사용, 소스·로그에 비밀번호/토큰/서명 URL 없음. 관리자 MFA·복구 절차는 시범 전 결정 |
| N-03 | 보존·무결성 | 계정 종료 후 자료 유지, 확정 정산 불변·정정 이력, 승인과 감사 로그의 트랜잭션, 버전 고정. 보존·삭제 기간은 O-08/O-09 |

## 로컬 착수 선택 (P, 2026-11-12)

조직·권한 첫 프로토타입은 React·TypeScript·Vite, FastAPI·Pydantic, SQLite와 명시적 SQL을 사용한다. Docker가 없는 현재 환경에서 가상 데이터의 권한·임기·영속성을 즉시 검증하기 위한 선택이다. 운영 DB·AWS 배포·Cognito는 미확정이며 SQLite 테스트를 PostgreSQL/AWS 검증으로 대체하지 않는다. 실행·범위는 [가이드](PROTOTYPE.md), 논리 모델·후속 상태 설계는 [상세 설계](design/PROTOTYPE_DESIGN.md)를 따른다.

## 2026-11-13 관리자 화면 보완 — S18

C-27: 담당 선생님의 담당자 등록 소속은 총학생회·학과협의회·신문방송국·연합동아리·모니터링단 5개 단체와 이후 추가한 운영 단체만 표시한다. 학과·학년·반은 제거하지 않고 역할의 세부 담당 범위로 분리한다. 선생님이 단체를 추가·삭제할 수 있다.

C-28: 전화번호 숫자 입력에 하이픈을 자동 적용한다. 담당자 제거 창의 질문은 ‘담당자를 제거하시겠습니까?’, 필수 확인 문구는 ‘제거하겠습니다’다. 사용자의 후속 지시 전까지 이번 변경은 로컬에만 유지하고 푸시하지 않는다.

P-05 구현 선택: 담당자 제거는 계정 비활성화·모든 세션 종료·해당 계정 역할 회수로 처리하며 역할·감사 이력을 보존한다. 관리자 계정 제거는 제외한다. 단체 삭제는 ‘삭제하겠습니다’ 확인 문구 입력 후 하위 단위와 함께 비활성화하고 해당 단체의 역할을 회수한다. 다른 단체·계정·과거 기록을 삭제하지 않는다. 같은 이름이 운영 중이면 중복을 차단하고, 삭제된 상태면 같은 ID와 하위 소속을 복원한다. 이전 역할·제거된 계정은 자동 복원하지 않으며 단체 복원을 별도로 감사 기록한다. 모니터링단·신설 단체의 구체 최고 책임자 직책과 회계 범위는 후속 확인하며 현재 일반 ‘최고 책임자’ 역할로 가상 시연한다.

기관 단체 소속으로 등록한 담당자에게 선생님·해당 최고 책임자가 최초 세부 역할을 부여하면 그 범위로 소속을 구체화한다. 소속만으로 업무 권한을 만들지 않고 기존 교차 단체·하위 담당자 재위임 제한을 유지한다. 역할 부여 성공·중복·입력 오류는 폼 안에서 표시한다.

## 실제 학번 로그인·최초 담당 선생님 계정 (검토 중, 2026-11-13)

사용자 요청: 실제 학교에 존재하는 학번으로 로그인할 수 있는지 검토하고 최초 담당 선생님 계정의 생성 방식을 정한다. 현재 가상 로컬 계정의 identifier는 등록한 문자열과 비밀번호만 확인하며 학교의 학적·재직 존재 여부를 검증하지 않는다. 선생님은 기존 Q53의 교직원 번호, 학생은 학번으로 구분한다.

O-02/O-12 확인 필요: 학교가 연동을 허용하는 SSO/학적·교직원 확인 API 또는 승인된 명부가 있는지, 계정 소유자 본인 확인과 최초 관리자 지정의 승인 주체. 번호 존재 여부와 해당 번호 소유자 본인 확인은 별개다. 학번 형식 일치나 이메일 주소 입력만으로 재학·재직 또는 관리자 자격을 확정하지 않는다.

P 구현 경로: 학교 SSO가 가능하면 학교 인증 결과와 고유 주체를 포털 계정에 연결한다. 승인 명부 방식이면 명부 대조에 더해 학교 이메일 인증·개별 초대 등 계정 소유 확인 절차를 정한다. 최초 선생님 계정은 운영자가 학교 승인과 교직원 신원을 확인한 뒤 지정하고, 공개 가입의 ‘선생님’ 선택이나 선착순 가입으로 관리자 권한을 부여하지 않는다. 실제 연동 정보가 없는 현재는 운영 인증 또는 실데이터 등록 기능을 구현한 것으로 보고하지 않는다.

AWS 후보는 Cognito의 SAML/OIDC 외부 인증 연동이다. 학교가 해당 방식과 연동 승인을 제공하는지는 아직 확인되지 않았다. [AWS 공식 문서](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-identity-federation.html). AWS 리소스 생성·운영 배포는 이번 작업 범위가 아니다.

사용자 답변 (2026-11-13): 학교 SSO/API·승인 명부 사용 가능 여부는 아직 확인 전이며 학교에 문의가 필요하다. 따라서 실제 학적·재직 검증과 운영 최초 관리자 등록은 연동 정보·승인 확인 전까지 미구현 상태로 둔다. 기존 로컬 가상 계정 로그인은 유지한다. 학교 문의 항목은 SSO/API 연동 허용, 학생·교직원 구분과 안정적인 고유 식별자 제공, 이용 승인 절차다.

## 담당자 등록 조건·복구·복수 소속·초대 (S19, 2026-11-13)

C-29: 학생 등록 학번은 숫자 8자리, 비밀번호는 8자 이상 숫자·특수문자 포함으로 검사한다. 여러 등록 소속을 선택할 수 있다. 삭제된 동일 계정은 복구하며 기존 역할은 자동 복원하지 않는다. 계정 동일성은 학번과 이메일 모두 일치하는 것으로 구현했다(P).

C-30: 사용자는 실제 이메일 검증과 초대 링크를 요청했고, 메일 서비스·발신 주소가 없어 로컬에서 초대·인증 흐름부터 검증하기로 답했다. 현재는 형식 검사와 로컬 초대 인증만 구현하며 실제 이메일 실존·소유를 검증한 것으로 표현하지 않는다. 실제 SMTP/SES 등 전송 연결은 후속이다. 신규·복구 계정은 초대 인증 후 로그인하고, 복구는 선생님만 가능하다. 기존 로컬 계정은 재검증 완료로 간주하지 않는 호환 예외로 유지한다.

링크는 24시간·1회 사용, 재발급 1분 제한의 초기 구현 선택(P)이다. 토큰 해시와 개발용 로컬 메일 미리보기를 구분하고 수신함 접근 범위를 검사한다. 세부 계약·운영 미결정은 [초대 인증 구현](design/INVITATIONS.md)을 따른다. 이 변경도 사용자 푸시 요청 전에는 로컬에만 유지한다.

## S20 역할 종류·하위 조직·범위 우선 부여 (2026-11-13)

C-31: 총학생회·신문방송국은 여러 부서의 부장·차장, 학과협의회는 학과별 학회장·부학회장·학년/반별 반대표, 동아리연합회는 연합회장 및 동아리별 회장·부회장·총무로 구성한다. 이전 일반동아리장→동아리원만의 설명은 최신 직책 구성으로 보완한다.

C-32: 담당 선생님은 역할 종류를 추가·삭제할 수 있고 선택한 단체/담당 범위에서 역할을 부여한다. 기존 최고 책임자·의장·학회장만의 관리자 부여 제한을 확대한다. 사용자 지정 역할명과 관리·회계 권한을 자동 연결하지 않는다. 의장의 선출·겸임·공식 임기는 그대로 보존한다.

P-06: 역할 종류를 단체·범위 종류별로 저장하고 삭제 시 해당 종류의 현재·예약 부여를 회수한다. 같은 종류 재등록은 정의만 복원하며 과거 권한은 되살리지 않는다. 최고 책임자·학회장의 추가 역할 부여 범위는 기존 관리 범위를 넘기지 않는다. 같은 단체의 복수 부서 겸임은 선생님·해당 최고 책임자의 명시적 역할 부여로 세부 소속을 추가한다. 하위 학회장의 소속 이동 권한을 확대하지 않는다. [상세 구현](design/ROLE_CATALOG.md).

C-33 (S21, 2026-11-13): 회수된 역할은 ‘역할과 임기’ 목록에 표시하지 않는다. API·감사·기존 부여 기록은 유지한다. 역할 부여의 자동 입력값은 한국 시간 기준 해당 연도 1월 1일~12월 31일이며 종료 당일까지 포함한다. API의 반개구간 저장은 유지하고 화면의 종료일 다음 날 00시로 변환한다. 의장과 학회장의 동일 공식 임기와 기존 시간값은 바꾸지 않는다.

## S22 학과협의회 간부진·학과 담당자·학회장 위임 (2026-11-13)

C-34: 학회장은 자기 학과의 학년·반을 등록하고 반대표 계정을 초대·등록하여 해당 반 역할을 부여할 수 있다. 반대표는 ‘1학년 A반 반대표’처럼 범위와 함께 표시한다.

C-35: 학회장·부학회장은 학과협의회 간부진과 각 학과 담당자 그룹에 함께 속한다. 반대표는 해당 학과 담당자 그룹에 속하고 협의회 간부진에는 포함하지 않는다. 향후 자료실에서 협의회 간부진 전용/학과별 공유를 구분한다. 구현은 현재 유효한 역할 기반 공유 대상이며 다른 학과의 계정·연락처 관리권을 자동 확대하지 않는다.

C-36: 학회장에게 의장 표시를 간단히 연결하는 화면을 제공한다. 선생님의 ‘의장 지정’에서 기존 학회장 자격과 공식 임기를 그대로 연결하고 선출 확인을 받는다. 의장만 해제하면 학회장은 유지한다. 기존 의장 선출·동일 임기·자격 종료 의존은 그대로다. 실제 자료실은 미구현이며 세부 계약은 [학과 공유 범위](design/ACADEMIC_SCOPES.md)를 따른다.

C-37 (S23, 2026-11-13): 등록한 하위 조직을 삭제할 수 있어야 한다. 구현은 삭제 권한이 있는 목록에 버튼과 확인창을 제공한다. 확인 방식은 최신 S24를 따른다. 자기 학과 학년/반은 학회장·의장이, 모든 하위 조직은 선생님이 관리한다. 하위 조직과 그 아래 조직의 역할을 함께 회수하고 계정·소속·이력을 보존한다(P). 같은 상위 조직·종류·이름의 재등록은 조직만 복원하며 이전 역할은 되살리지 않는다. 상위 조직 복원으로 그 전에 별도 삭제한 하위 조직을 복구하지 않도록 삭제 묶음을 구분한다(P). 이번 추가 변경의 자동 커밋·푸시는 하지 않는다.

C-38 (S24, 2026-11-13): 하위 조직 삭제는 강조한 ‘정말로 삭제하시겠습니까?’와 유의사항을 안내하고 ‘유의사항을 확인했으며, 삭제하겠습니다.’ 체크 후 삭제 버튼으로 실행한다. 산하 조직 동반 삭제·현재/예약 역할 회수·학회장 자격에 연결된 의장 종료·계정/과거 기록 보존·복원 시 역할 재부여·독립 삭제 하위 조직의 복원 제외를 알린다. 체크만으로 삭제하지 않으며 창을 다시 열면 동의를 초기화한다(P). 서버도 명시적 confirmed=true를 검사한다(P). 단체·담당자·역할 종류 확인 방식은 이번 변경 대상이 아니다. 커밋·푸시는 하지 않는다.

C-39 (S25, 2026-11-13): 역할과 임기는 단체별 선택 후 해당 인원만 표시한다. 담당자 목록은 현재 유효한 자치단체장(최고 책임자·의장)을 먼저 표시하고 더보기로 나머지를 펼친다. 이름과 단체명으로 검색하며 검색 중에는 접힌 담당자도 결과에 포함한다. 복수 소속은 각각의 단체명으로 찾되 한 사람은 한 행으로 표시한다. 기존 서버의 조회·개인정보 범위는 그대로 유지한다. 구현 P: 최초에는 단체 선택 안내를 표시하고 역할 부여 성공 시 해당 단체를 선택한다. 신규/복구 등록 직후에는 등록 결과를 볼 수 있도록 목록을 펼친다. 검색 해제 시 기본 목록으로 돌아간다. 커밋·푸시는 하지 않는다.

P-11 (S26, 2026-11-13): 사용자가 학과 아래에 1A·3SAP를 등록했으나 학년 종류로 저장되어 반대표 대상에서 제외됨을 확인했다. 학과→학년→반 구조는 유지하며 새 등록의 종류·예시·순서를 명확히 안내한다. 학년에 숫자+영문 반 표기를 등록하는 것은 화면/서버에서 거절한다. 기존 데이터는 자동 변경하지 않고 사용자가 ‘반으로 변경’에서 같은 학과의 활성 학년과 반 이름을 확인해 이동한다. ID·소속을 유지하고 변경 전후 감사를 남기며, 산하 조직 또는 과거를 포함한 역할 이력이 있으면 거절한다. 같은 이름의 기존/삭제 반과 합치지 않는다. 필요한 학년이 없으면 등록·복원부터 안내하고 삭제된 학년의 복원 효과를 알린다. 새 반 등록/복원·변경 성공 시 반대표 역할과 범위를 자동 선택하며 실제 부여는 대상/임기 확인 후 기존 API로 수행한다. 의장·학회장의 기존 관리 범위를 확대하지 않는다. 로컬 실제 자료는 자동 변환하지 않았으며 커밋·푸시는 하지 않는다.

## 2. 목표, 범위, 사용자

기존 임원에게 연락해 파일을 찾거나 매년 개인 저장소를 복사하는 부담을 줄인다. 조직·학년도·행사별 자료와 예산을 한 포털에서 관리하고, 다음 임원이 기록을 읽고 업무를 시작할 수 있어야 한다.

초기 개발·시연 조직은 **학과협의회와 총학생회**를 권장한다. 실제 시범은 그중 1~2개 조직부터 시작하고 나머지 조직도 동일 모델로 수용한다. 조직 간 상하 관계와 전 조직 감독권은 아직 정의하지 않는다.

확인된 구성은 각 단체의 최고 책임자, 총학생회·신문방송국의 부장·차장, 학과협의회의 학회장·부학회장·반대표, 연합동아리의 일반동아리장·동아리원과 학생성공센터 담당 선생님이다. 첫 버전은 이들 중 운영 담당자를 중심으로 사용한다(C-11). 담당 선생님이 4개 최고 책임자 권한을 부여하고, 각 최고 책임자가 자기 단체의 하위 역할을 부여한다(C-12/13). 학회장은 부학회장·반대표를 직접 지정한다(C-14). 의장(학과협의회장)은 자기 학과 학회장을 겸한다(C-15). 참여 하위 직책과 자료·회계 기능은 추가 확인한다. 단체 간 상하 관계나 총학생회의 타 단체 감독권은 부여하지 않은 초안이다. 일반 학생 공개 포털은 초기 범위 밖이다.

최신 조직 구조와 사실/제안/미결정 구분은 [조직 구조·운영 주체](ORGANIZATION_MODEL.md)를 따른다.

### 회계 규칙 초안 (P, O-04 결정 대상)

- 금액은 KRW 정수이며 부동소수점을 쓰지 않는다. 예산·지출은 양수, 환불·정정은 유형과 원본 참조로 구분한다.
- 행사 배정은 연간 예산의 하위 배분이다. 연간 총액과 행사 배정액을 더해 예산을 이중 계산하지 않는다. 행사 배정 합계는 연간 총예산 이하로 제한한다.
- 승인액 = 승인된 지출 + 승인된 정정의 순증감. 잔액 = 배정 예산 − 승인액. 제출 대기액은 별도로 표시하고, 아직 실제 잔액에서 차감하지 않는 기준안을 사용한다.
- 승인 시 해당 행사 배정과 연간 총예산을 모두 검사하고 잠금/원자적 갱신으로 동시 승인에 따른 초과를 막는다. 예산 감액도 승인액보다 작게 할 수 없다.
- 지출 상태는 `DRAFT → SUBMITTED → APPROVED | REJECTED`. 반려 후 수정·재제출은 새 제출 회차를 만들고 과거 신청·판정은 남긴다. 제출 상태에서는 금액·증빙을 임의 변경하지 않는다.
- 작성자는 자기 지출·정정을 승인할 수 없다. 승인자 부재 시 임의 자기승인 대신 다른 승인자 지정 문제를 해결한다.
- 정산 확정은 미처리 제출·증빙 누락 점검 후 실행한다. 확정 지출·정산 원본은 덮어쓰지 않는다. 승인된 정정은 원본 참조·사유·승인자·증감·적용일과 별도 개정 정산으로 남긴다.
- 회계연도와 학년도 관계, 현금·발생 기준, 실제 지급 완료 상태, 환불 기준은 추후 회계 담당과 결정한다. 이 포털은 1차에서 실제 지급을 수행하지 않는다.

### 인수인계 규칙 초안 (R/P, O-03·O-12 결정 대상)

1. 전년도 운영기와 다음 운영기를 연결한다. 새 운영기 생성만으로 권한을 일괄 복제하지 않는다.
2. 인계자가 문서 버전, 확정 정산, 계속할 업무, 주의 사항을 체크리스트로 묶어 제출한다.
3. 지정 책임자가 인수자와 역할을 승인한다. 임시 인수 접근이 필요하면 범위·기한을 별도 부여한다.
4. 인수자는 허용된 과거 자료를 열람하고 항목별 확인한다. 완료는 양측 확인과 필수 항목 충족 후 기록한다.
5. 기존 소속은 임기 종료 또는 명시적 회수 시점부터 일반 권한이 종료된다. 인수인계 미완료가 기존 권한을 무기한 연장하지 않는다. 유예는 별도 승인한다.
6. 다음 운영기의 유효 소속은 같은 조직의 과거 자료를 읽을 수 있도록 제안한다. 영수증·민감 문서는 회계 역할 등 추가 제한을 적용한다. 과거 운영기의 원본 수정권은 자동 승계하지 않는다.
7. 조직 자료 ID·소유 조직과 감사 이력을 유지한다. 계정 삭제·비활성화는 조직 자료를 삭제하지 않는다. 중도 교체에도 같은 원칙을 적용한다.

## 4. 권한 체계 초안

**S10의 확정사항:** 담당자 중심 사용, 담당 선생님은 서비스 관리자, 선생님이 4개 최고 책임자 역할을 부여, 최고 책임자가 자기 단체의 하위 역할을 부여한다. S11/S12에서 학회장의 부학회장·반대표 지정과 의장·학회장 겸임을 추가 확정했다. [역할·권한 명세](ACCESS_CONTROL.md)의 확정 부여표를 따른다. 아래의 기능별 권한 매트릭스는 계속 P이며 확정 역할 부여 체계를 바꾸지 않는다.

역할명과 매트릭스는 **P**다. 학생회장·의장·국장·연합동아리장은 확인된 직책이고, 권한 묶음과 별도로 관리한다. 최고 책임자의 자기 단체 예산 관리 권한을 명세에 반영해야 하지만 간부의 입력 위임·별도 승인자·자기승인 정책은 O-02/O-04에서 결정한다.

단체별 직책 순서는 C-08의 조직 구조다. 아래 역할은 직책명과 일대일 대응하지 않으며, 동아리원을 자동으로 EDITOR로 매핑하거나 상위 직책에 하위의 모든 자료 열람권을 부여하지 않는다. 학과·분반·개별 동아리 범위는 O-13에서 결정한다.

담당 선생님은 C-09/12에 따라 서비스 관리자다. 아래 PLATFORM_ADMIN은 기술 배포·장애 대응 권한의 기존 제안이며, 서비스의 사용자·역할 관리 권한과 구분한다. 서비스 관리자의 문서·회계 기능은 O-01에서 추가 결정한다. 최고 책임자는 자기 단체 하위 역할을 부여하고, 학회장은 부학회장·반대표를 부여한다. 그 밖의 하위 담당자 재위임은 O-02에서 결정한다. 의장과 자기 학과 학회장은 동일 사용자의 별도 역할로 표현한다. 사용자는 여러 소속과 역할을 가질 수 있다.

- 계정 활성, 소속 승인, 서버 시각 기준 `starts_at <= now < ends_at`, 미회수 상태, 대상 조직·운영기·상태 일치. 계정 로그인 성공만으로는 충분하지 않다.
- 작성·수정은 현재의 열린 운영기에 한정한다. 과거 운영기는 읽기 및 승인된 정정만 허용한다. 파일·영수증·버전·공유·검색·집계·내보내기에도 같은 검사를 적용한다.
- 학회장의 부학회장·반대표 지정은 자기 학과 범위로 제한하는 P다. 의장 겸임자의 협의회 범위 권한과 학회장 단독 역할의 자기 학과 범위를 별도로 판정한다. 의장 역할과 학회장 역할의 만료·회수도 각각 평가한다.
- 최고 책임자는 자기 단체의 하위 역할만 부여하는 기준을 적용한다. 타 단체·서비스 관리자·동급 최고 책임자 권한 부여, 자기 권한 확대는 허용하지 않는 P다. 최고 책임자 임명은 담당 선생님이 수행한다. 최초 관리자·회수·재위임·회계 기능 권한은 O-02/O-12에 따라 결정한다.
- 공통 공유는 인증된 지정 조직의 읽기 허용이다. 누구나 읽는 인터넷 공개와 다르며, 공유받은 조직이 원본을 수정하거나 재공유하지 못한다. 공유 철회 후 신규 접근을 차단한다.
- Cognito는 신원 확인에 사용하고, 조직·임기·동적 역할은 애플리케이션 DB에서 판정하는 R/P다. JWT에 남아 있는 이전 역할만 믿지 않는다.
- 회수 후 다음 API 요청과 신규 파일 URL 발급을 차단한다. 이미 발급한 Presigned URL은 유효기간 동안 사용될 수 있으므로 제안 TTL은 최대 5분이다. 즉시 파일 차단이 필요한 정책이면 인증 프록시 등 다른 전달 방식을 검토한다. [AWS Presigned URL 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
- URL 발급 이력은 ‘다운로드 권한 발급’이다. 사용자가 파일을 끝까지 읽었다는 증거와 구분한다.

## 5. 논리 데이터 모델 초안

PostgreSQL을 우선 검토하는 **P**이며 확정 DDL은 아니다. 아래는 논리 엔터티 목록으로, 마이그레이션은 구현 단계에 맞춰 나눈다. 모든 조직 업무 엔터티에 조직 범위를 명시하고 UUID 등 추측하기 어려운 ID를 사용하되 ID 자체를 접근 통제로 간주하지 않는다.

| 엔터티 | 주요 필드 | 관계·제약 |
|---|---|---|
| User | id, auth_subject, display_name, email, status | 인증 subject 유일. 개인정보 최소화. 조직 자료에 삭제 연쇄 없음 |
| Organization | id, code, name, status | 연도가 바뀌어도 동일 ID 유지 |
| AcademicYear | id, label, starts_at, ends_at | 학교의 실제 학년도 경계 O-03 |
| OrganizationTerm | id, organization_id, academic_year_id, status | 조직+학년도 유일 제안. DRAFT/OPEN/CLOSED |
| Membership | id, user_id, organization_term_id, position_title, starts_at, ends_at, status, approved_by, revoked_at | 소속과 임기. 사용자+운영기 중복 방지, 역할은 별도 |
| MembershipRole | id, membership_id, role, scope_id?, granted_by, granted_at, starts_at, ends_at, revoked_by?, revoked_at?, reason | 동일 사용자의 의장(협의회)·학회장(학과) 겸임을 별도 부여로 표현하는 P. 학회장 역할은 학과 범위 필수. 역할+범위의 유효 중복 방지, 각 역할의 임기·회수 분리 |
| ServiceAdminAssignment (P) | user_id, starts_at, ends_at, assigned_by, revoked_at | 담당 선생님의 서비스 관리자 역할 표현안. 최초 등록·관리자 교체는 O-12. 기술 플랫폼 운영권과 구분 |
| PlatformRoleAssignment | user_id, role, starts_at, ends_at, granted_by | 조직 업무 열람권을 자동 부여하지 않음 |
| StaffScopeAssignment (P) | user_id, organization_id, capability, starts_at, ends_at, granted_by | 담당 선생님과 단체별 업무 권한을 연결하는 제안. 구체 capability는 O-01에서 결정. 학생 임기와 분리 |
| Folder | id, organization_term_id, parent_id, name | 같은 운영기의 부모만 참조, 순환 금지 |
| Event | id, organization_term_id, title, starts_at, ends_at | 1차에서는 자료·예산 묶음 |
| Document | id, organization_term_id, folder_id, event_id?, type, title, description, created_by, current_version_id, status | 소유자는 운영기를 통한 조직. 작성자와 소유권 분리 |
| DocumentVersion | id, document_id, version_no, file_object_id, uploaded_by, created_at, change_note | 문서+버전번호 유일. 변경 대신 새 버전, 복원도 새 버전 |
| FileObject | id, organization_id, object_key, storage_version_id, original_name, size, content_type, checksum, status, uploaded_by | 객체키 유일. 증빙 파일도 사용. 외부 URL은 영구 저장하지 않음 |
| DocumentShare | document_id, target_organization_id, granted_by, granted_at, revoked_at | 허용된 일반 문서에만 읽기 공유. 영수증의 공유 우회 방지 |
| AnnualBudget | id, organization_term_id, responsible_membership_id, currency, total_amount, revision | 예산 관리 책임 소속은 해당 운영기의 최고 책임자로 연결하는 P. 원본은 조직에 귀속하고 책임자 교체 이력 보존. 증액·감액 이력 별도 |
| BudgetAllocation | id, annual_budget_id, event_id?, label, amount | 행사/운영비 배정. 배정 합계 ≤ 총액, 같은 운영기만 연결 |
| Expense | id, allocation_id, created_by, occurred_on, current_revision_id, status | 직접 덮어쓰지 않고 제출 회차와 판정을 연결 |
| ExpenseRevision | id, expense_id, revision_no, purpose, amount, submitted_at | 승인 대상의 금액·내용 스냅샷. expense+회차 유일 |
| ExpenseAttachment | expense_revision_id, file_object_id | 제출 회차에 증빙 고정. 같은 조직의 READY 파일만 참조 |
| ApprovalDecision | id, expense_revision_id 또는 correction_id, actor_id, result, reason, decided_at | 대상 중 정확히 하나만 지정. 중복 최종 판정 방지, 자기승인 금지 |
| Settlement | id, organization_term_id, revision_no, cutoff_at, snapshot, finalized_by, finalized_at | 확정 시점 집계 보존. 이후 정정 시 새 개정판 |
| AccountingCorrection | id, original_expense_id, original_settlement_id?, delta_amount, reason, status, created_by | 원본 유지, 별도 승인. 반영 순증감과 정산 개정 추적 |
| Handover | id, organization_id, from_term_id, to_term_id, status, submitted_by, accepted_by, completed_at | 같은 조직, 서로 다른 운영기. DRAFT/SUBMITTED/ACCEPTED/COMPLETED |
| HandoverItem | id, handover_id, type, document_version_id?, settlement_id?, task_text?, required, checked_by, checked_at | 자료·정산 버전 고정 또는 업무 메모. 같은 조직 범위 검증 |
| AuditEvent | id, actor_id?, actor_label, organization_id?, action, target_type, target_id, occurred_at, request_id, change_summary | 업무 이력 추가 전용. 민감 원문·토큰 저장 금지 |
| ProcessedEvent / OutboxEvent | dedupe_key, target_id, status, attempts, created_at | 파일 이벤트 중복 억제 / DB 저장과 알림 발행 사이 유실 방지. 비동기 도입 시 추가 |

S9의 상세 직책은 Membership의 직책 정보로 표현하는 안이다. 학회장의 역할 부여 범위 검증을 위해 최소한 학회장과 자기 학과의 연결은 필요하다. 학과·반·개별 동아리별 자료 분리의 세부 구조는 추가 검토한다. 하위 조직 수·구조·참여 하위 담당자는 O-13 미정이며 현재 표를 최종 ERD로 확정하지 않는다.

`?`는 선택 필드다. 일부 엔터티의 조직·운영기는 부모에서 도출할 수 있다. 물리 모델에서 중복 저장한다면 복합 외래키 등으로 일치를 강제한다.

관계 요약:

```text
User ─ Membership ─ OrganizationTerm ─ Organization
            │               ├─ Folder / Event ─ Document ─ DocumentVersion ─ FileObject
       MembershipRole       ├─ AnnualBudget ─ BudgetAllocation ─ Expense ─ ExpenseRevision
                            │                                      ├─ ExpenseAttachment ─ FileObject
                            │                                      └─ ApprovalDecision
                            └─ Settlement ← AccountingCorrection → ApprovalDecision
Organization ─ Handover(from_term, to_term) ─ HandoverItem
Document ─ DocumentShare ─ target Organization
각 변경 행위 ─ AuditEvent
```

구현 시 지켜야 할 무결성:

- 문서·폴더·행사·배정·지출·증빙·인수인계 참조의 조직과 운영기 일치를 서버와 DB에서 검증한다. 타 조직 ID를 정상 요청 본문에 끼워 넣어도 거부한다.
- 사용자/소속 종료 시 조직·문서·예산·정산·감사 이력의 `ON DELETE CASCADE`를 금지한다. 개인정보 삭제는 작성자 식별정보의 가명화 등 별도 정책으로 처리한다.
- 금액 합계·승인 전이·예산 감액·소속 활성화/회수·인수인계 완료는 동시성을 고려한 트랜잭션으로 처리한다. 감사 이벤트도 성공한 변경과 함께 커밋한다.
- UTC 시각 저장, 화면은 Asia/Seoul. 학년도와 날짜만 있는 지출일은 시간대 변환 대상과 구분한다.
- 검색 인덱스는 조직·운영기·문서 유형·제목·상태, 회계는 배정·상태·일자 중심으로 제안한다. 권한 필터를 페이지 처리·집계보다 먼저 적용한다.
- 인수인계는 기존 자료 참조를 보존한다. 새 운영기에는 새 예산·새 문서를 만들며 전년도 지출을 당해 연도 지출로 복사하지 않는다.

## 6. 화면·API 구현의 경계

화면 초안은 로그인/초대 확인, 조직·학년도 선택, 조직 대시보드, 자료실·상세·버전, 예산·지출·승인함, 인수인계 목록·상세, 조직 구성원 관리, 운영 상태 화면이다. 조직과 학년도 선택은 탐색 편의이며 인가의 근거가 아니다.

REST 경로 초안은 `/organizations/{org_id}/terms/{term_id}/...` 아래 `documents`, `upload-sessions`, `budgets`, `expenses`, `handovers`, `memberships`를 둔다. 승인·반려·정산 확정·역할 회수는 명시적 명령으로 처리한다. 리소스 ID만 받는 경로도 소유 조직을 조회하여 검사한다.

오류는 인증 실패 401, 권한 실패 403 또는 존재 노출을 막는 일관된 404, 충돌·종료된 상태 409, 잘못된 입력 422 등으로 계약을 정한다. 페이지 크기 상한, 요청 추적 ID, 동시 수정 충돌, 제출·승인 중복 요청 처리 규칙을 API 명세에 담는다. 최종 경로·어댑터·라이브러리 버전은 구현 전 결정한다.

## 7. AWS 아키텍처 권장안

아래는 **R/P의 배포 후보**다. 프론트엔드와 API 실행은 서버리스 중심이지만 RDS·네트워크는 상시 비용이 발생할 수 있는 관리형 자원이다. 전체를 ‘유휴 비용 없는 서버리스’로 간주하지 않는다.

```text
브라우저 ─HTTPS─ CloudFront ─OAC─ S3 웹 버킷 (비공개, 정적 빌드)
   ├─ Cognito (로그인, 토큰)
   ├─ API Gateway (토큰 검증)
   │     └─ Lambda / FastAPI 연동 어댑터 (업무 인가)
   │            ├─ VPC 내부 RDS PostgreSQL (연결 수 제어, Proxy 검토)
   │            ├─ 파일 URL 서명 / 파일 메타데이터
   │            └─ CloudWatch 로그·지표·알림
   └─ 권한 확인 후 발급된 URL ─ S3 문서·증빙 버킷 (비공개)
                                       └─ SQS Standard ─ Lambda 파일 처리 ─ DB 상태
                                              └─ DLQ (실패 대기열)

선택 확장: 승인 이벤트/Outbox ─ SNS 또는 Step Functions ─ 알림
           EventBridge Scheduler ─ 정기 보고서 Lambda
공통 기반: IAM 최소 권한, VPC·Security Groups, 비밀정보 관리, 백업, 비용 관리
```

### 서비스별 역할과 선택 조건

| 영역 | 권장안 | 구현·검증 포인트 |
|---|---|---|
| 웹 | React + TypeScript, Vite 후보 / S3 + CloudFront | 정적 빌드, HTTPS, SPA 라우팅, 배포 롤백. 문서 버킷과 웹 버킷 분리 |
| 인증 | Cognito | 가입 정책·MFA·계정 복구 결정. 인증과 업무 인가 분리. 학교 SSO는 별도 |
| API·계산 | API Gateway + Lambda / Python + FastAPI | HTTP API/REST API의 인증·비용·제한 비교, Lambda 어댑터와 런타임 검증. 장시간 파일 처리는 요청에서 분리 |
| 데이터 | RDS PostgreSQL 우선 | 관계·트랜잭션·집계 장점. Private DB, TLS, 마이그레이션, 연결·동시성 제한 |
| 파일 | 비공개 S3, Versioning, 짧은 Presigned URL | 공개 차단, 서버 지정 객체키, 형식·크기·체크섬 검증, 실제 버전 ID와 문서 버전 연결 |
| 비동기 | SQS Standard + Lambda + DLQ | 중복·역순·재시도·부분 실패·재처리. 파일 검증 목적을 구체적으로 구현 |
| 승인·알림 | 처음에는 DB 상태 전이, 필요 시 SNS·Step Functions | 승인 자체는 API에서 재인가. 이메일 구독·발송 허용 조건 확인. 알림 실패가 승인 중복을 만들지 않음 |
| 정기 자동화 | EventBridge Scheduler, 후속 | 실제 정기 보고 요구가 생길 때 도입 |
| 모니터링 | CloudWatch | 요청 오류·지연, Lambda 실패·스로틀, DB 연결, 큐 적체·DLQ·비용 알림의 전달 확인 |
| 배포 관리 | IaC + CI/CD 후보 | SAM/CDK/Terraform 중 선택 O-06. 환경 분리, 검증·마이그레이션·배포·롤백, 장기 AWS 키 최소화 |

### 연결과 보안에서 빠뜨리면 안 되는 사항

1. **웹 원본과 업무 파일을 분리한다.** CloudFront OAC는 S3 원본 보호이며 조직별 업무 인가를 대신하지 않는다. 웹은 일반 S3 버킷 원본을 사용한다. S3 website endpoint에는 OAC를 적용할 수 없다. [AWS OAC 문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html)
2. **Lambda ↔ RDS 연결을 실험한다.** 같은 VPC의 허용된 Security Group 경로에서 DB에 접근하고 동시 연결 수를 제한한다. RDS Proxy는 연결 풀 후보로 비용·권한·부하를 비교한다. 단순 실습에서는 제한된 직접 연결도 검토한다. [AWS Lambda–RDS 문서](https://docs.aws.amazon.com/lambda/latest/dg/services-rds.html)
3. **VPC 외부 서비스 경로를 명시한다.** DB 연결 Lambda가 S3·SQS·비밀정보 등 필요한 API에 접근하는 방법을 VPC endpoint 또는 NAT 등으로 설계하고 비용을 산정한다. 퍼블릭 서브넷 배치만으로 해결된다고 가정하지 않는다. JWT의 외부 키 조회 등 필요한 outbound도 확인한다.
4. **업로드는 준비 → 전송 → 검증 → 권한 있는 사용자에게 제공 가능한 상태로 나눈다.** API가 업로드 세션과 객체키를 만든 뒤 브라우저가 직접 S3로 전송한다. 클라이언트 완료 신호만 믿지 않고 파일·크기·체크섬·버전을 서버에서 확인한다. `PENDING → PROCESSING → READY | REJECTED`를 표시하고 READY 전 다운로드·증빙 제출을 제한한다. 검사 방식은 O-09에서 결정하며 메타데이터 확인을 악성파일 검사 완료라고 표현하지 않는다.
5. **서명 URL을 일회용이라고 부르지 않는다.** 만료까지 재사용될 수 있다. 업로드 객체키 재사용·덮어쓰기를 고려하여 불변 버전키와 저장소 버전 ID를 고정하고, 서버가 검증한 버전만 다운로드한다. URL·토큰을 로그에 저장하지 않는다. [AWS Presigned URL 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
6. **파일 이벤트는 중복·지연·역순을 허용하는 소비자로 처리한다.** 객체/버전 기반 멱등키, 같은 객체의 순서 비교, 처리 결과 조건부 갱신과 DLQ 재처리를 설계한다. S3 알림은 적어도 한 번 전달되며 Standard SQS를 직접 연결한다. FIFO가 필요하면 별도 라우팅을 검토한다. [AWS S3 알림](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html), [이벤트 순서 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html)
7. **버전 관리와 복구 계획을 함께 만든다.** S3 Versioning은 이전 객체 복원에 쓰고, 비용·삭제 권한·보존 정책을 별도 설정한다. RDS 시점 복구는 새 DB 인스턴스를 만들므로 연결 전환·문서 버전 정합성까지 훈련한다. 버전 관리만으로 모든 삭제·계정 사고에 대비한 독립 백업이 완성되지는 않는다. [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html), [RDS 시점 복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

### 환경·비용·대안

- 로컬 개발은 PostgreSQL과 테스트 파일 저장소/스토리지 어댑터로 핵심 규칙을 검증하는 안이다. 로컬 모의 통과와 실제 AWS 통합 검증을 구분한다.
- 과제 계정에서 Cognito·IAM·VPC·RDS·SQS 등 생성·실행 권한과 세션/계정 종료 조건을 확인한다. Learner Lab을 장기 운영 계정으로 전제하지 않는 R-05를 유지한다. 정확한 이용 제약은 해당 수업 계정에서 확인한다.
- 리전·DB 사양·가동 시간·파일/버전 용량·트래픽·로그 보존량을 정한 뒤 견적을 낸다. RDS·Proxy·NAT·VPC endpoint·백업 비용을 포함한다. 무료 운영이나 특정 월 비용을 보장하지 않는다.
- 월 상한과 알림 수신자를 O-05에서 결정한다. 예산 알림은 비용을 강제로 차단하는 장치로 취급하지 않는다. 임시 자원 종료 전 데이터 내보내기·복구 가능 여부를 확인한다.
- RDS 비용·권한이 맞지 않으면 DynamoDB를 비교할 수 있으나 승인 원자성·관계·집계·조회 패턴을 다시 설계해야 한다. DB만 교체하면 된다고 가정하지 않는다.
- 수업에서 EC2/ALB/Auto Scaling 시연이 실제로 요구될 때 계산 계층 대안을 검토한다. 기존 사례에 등장했다는 이유만으로 필수 기능으로 추가하지 않는다.

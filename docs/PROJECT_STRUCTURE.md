# 연이음 프로젝트 구조

작성: 2026-11-12. 적용 상태: 디렉터리 시작점·배치 규칙·공통 파일 검사 반영. 조직·권한 웹/API 로컬 앱은 추가했고 AWS 자원은 아직 구현하지 않았다.

## 선택한 구조

한 저장소에서 웹·API·인프라를 분리하고, 각 앱 내부는 기능 중심으로 확장한다. 기능 내부에 필요한 라우터·서비스·입출력·모델을 두는 혼합 구조다. 우선 하나의 API로 개발하며, 조직이나 기능마다 별도 서비스를 만들지 않는다.

```text
yeonieum/
├── apps/
│   ├── web/
│   │   ├── src/
│   │   │   ├── features/          기능별 UI·상태·API 호출
│   │   │   └── shared/            실제로 재사용되는 UI·기반 기능
│   │   ├── public/                공개 가능한 웹 정적 파일
│   │   ├── tests/                 웹 통합 테스트
│   │   └── README.md
│   └── api/
│       ├── src/yeonieum/
│       │   ├── modules/           기능별 API·업무 로직·모델
│       │   └── core/              설정·로그·DB 연결 등 기반 기능
│       ├── tests/                 API 단위·통합 테스트
│       └── README.md
├── infra/                        AWS IaC·배포 구성
├── tests/
│   ├── e2e/                      웹/API를 함께 검증하는 사용자 흐름
│   └── unit/                     저장소 개발 도구의 단위·Git 동작 검증
├── scripts/                      반복하는 개발·검증·운영 작업
├── docs/                         요구·권한·구조·운영 문서
├── .github/workflows/quality.yml  공통 검사 CI
├── .editorconfig
├── .gitattributes
├── .gitignore
├── .pre-commit-config.yaml
├── requirements-dev.txt          공통 검사 도구 의존성
├── CONTRIBUTING.md
├── AGENTS.md
├── GLOSSARY.md
└── README.md
```

빈 시작 디렉터리는 `.gitkeep`으로 Git에 보존한다. 아래의 구체 기능 폴더·앱 의존성·프레임워크 설정은 구현할 때 만든다. Python API 경로는 기존 권장안에 맞춘 시작점이며, 로컬의 임시 기술 선택과 검증 범위는 [실행 가이드](PROTOTYPE.md)와 개발 브리프에 기록한다.

## 기능별 배치 지도

| 기능 이름 | 책임 | 요구 연결 |
|---|---|---|
| access | 사용자·초대·소속 역할·범위·유효기간 판정 | M-01~03, F-01/02, AUTH |
| organizations | 단체·학과·반·부서·동아리 단위와 학년도 분류 | M-03, F-02 |
| documents | 자료·파일 메타데이터·버전·검색·휴지통 | M-04~06, F-03/04/10 |
| budgets | 연간·행사 예산·지출·증빙 참조·확인·정산·정정 | M-07~09, F-05/06 |
| handovers | 인계·인수 목록·필수 확인·권한 교체 절차 | M-10/11, F-07 |
| knowledge | 승인 자료 기반 RAG와 근거·권한·반영 상태 | 핵심 완료 후의 AI 확장 |

이 이름은 웹 `src/features/<기능>`와 API `src/yeonieum/modules/<기능>`에서 같은 의미로 사용한다. 양쪽의 내부 파일 이름까지 똑같이 강제하지 않는다. 실제 기능이 생길 때만 해당 디렉터리를 만든다.

API 기능 내부의 예시:

```text
modules/documents/
├── router.py       HTTP 입력·출력·요청 인가 연결
├── service.py      문서 상태·버전·업무 규칙
├── schemas.py      요청·응답 계약
└── models.py       필요해졌을 때 추가할 저장 모델
```

모든 기능에 같은 파일을 먼저 만들 필요는 없다. 저장 경계가 복잡해지거나 대체 구현이 실제로 필요할 때 repository/adapter 등을 추가한다. 기능 하나를 수정할 때 대부분 그 폴더 안에서 작업할 수 있게 한다.

## 의존성과 공통 코드

- 화면/HTTP 어댑터가 업무 서비스를 호출하고, 서비스는 명확한 입출력으로 다른 기능과 협력한다. 저장 모델과 HTTP 응답 객체를 무제한으로 전파하지 않는다.
- 권한 판정은 access의 명시적 인터페이스를 사용하고, documents/budgets/handovers에서 대상의 소유 범위와 상태도 확인한다.
- 영수증은 documents의 파일 ID·버전을 참조한다. budgets가 documents 내부 저장 코드를 직접 수정하지 않는다.
- `core`에는 설정·로그·DB 연결 같은 기반 기능을 둔다. 예산 계산·자료 소유권·인수 확인 같은 업무 규칙은 담당 기능에 둔다.
- `shared`에는 실제 여러 기능이 재사용하는 코드만 올린다. `utils`, `misc`, `stuff`에 관련 없는 코드를 모으지 않는다.
- 구조 때문에 순환 의존성이 생기면 인터페이스와 책임을 먼저 조정한다. 전역 싱글턴이나 다른 기능의 내부 파일 직접 참조로 감추지 않는다.

## 테스트·설정·리소스

웹 단위 테스트는 기능 가까이에 두고, 웹 통합 테스트는 `apps/web/tests`, API 테스트는 `apps/api/tests`, 실제 사용자 흐름은 `tests/e2e`에 둔다. 기존 [수용 기준](ACCEPTANCE.md)의 요구·테스트 ID를 연결한다.

도구가 루트에서 찾는 설정은 루트에, 앱 전용 설정·의존성은 해당 앱에 둔다. 의미 없는 공통 `config/` 폴더를 추가하지 않는다. 개발·테스트·운영의 비밀은 환경 변수·선택한 비밀 저장소로 주입한다. 공개 가능한 기본값과 비밀이 없는 `.env.example`만 커밋한다.

공개 로고·폰트는 웹의 public 또는 실제 번들 자산 위치에 둔다. 학교 문서·영수증을 웹 정적 파일에 넣지 않는다. 파일 저장소와 백업은 런타임 데이터이며 Git 자산과 분리한다.

## 문서와 자동화

[기여 가이드](../CONTRIBUTING.md)에 이름·검사·리뷰 규칙을 둔다. 요구·권한·수용 기준의 기존 문서 경로는 유지했다. 실행 명령·API 계약·배포 절차는 구현과 같은 변경에서 갱신한다. FastAPI를 선택하면 실제 OpenAPI를 API 문서로 연결하는 등 프레임워크의 기본 기능을 활용한다.

공통 훅과 CI는 현재 존재하는 파일만 검사한다. 앱 코드 도입 시 앱별 린트·포맷·타입 검사·테스트를 추가한다. 배포 CD는 AWS 계정·환경·IaC가 정해진 뒤 구성하고, 현재 CI가 배포까지 수행한다고 표현하지 않는다.

## 구조 변경 원칙

작은 기능 변경은 관련 폴더만 수정한다. 기존 파일을 옮길 때 참조·테스트·빌드·문서 경로를 함께 갱신하고 관련 검증을 실행한다. 중복 폴더와 장기적인 임시 호환 계층을 남기지 않는다. ADR은 되돌리기 어렵고 설명이 필요한 실제 선택이 생겼을 때만 추가한다.

이 문서는 구조와 개발 관례를 적용한 것이다. 이전 인터뷰의 기능·권한 합의 전체를 최종 명세 v1.0으로 확정한 문서로 취급하지 않는다. 최신 사용자 결정이 0.x 명세와 다르면 최신 결정을 우선하고 관련 명세 동기화를 명시적으로 수행한다.

Git 브랜치·커밋·PR·배포 경계는 [Git 협업 규칙](GIT_WORKFLOW.md)에 둔다. 저장소 도구 테스트는 `tests/unit`에서, 앱의 업무 테스트는 각 앱에서 검증한다.
